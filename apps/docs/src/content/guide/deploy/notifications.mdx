How a run tells someone it finished, and the destinations an operator shares between agents.

## Completion webhooks

A durable run can announce its end to endpoints its manifest names in `spec.execution.webhooks`.
The manifest carries only ids; the operator registers what each id means:

```bash
FELIX_WEBHOOK_ENDPOINTS='{
  "ops":   {"url": "https://hooks.example.com/felix", "secret": "secret:OPS_WEBHOOK", "tenants": ["acme"]},
  "audit": {"url": "http://audit.internal:8080/runs", "secret": "whsec_...", "tenants": "*", "private": true}
}'
```

| Key | Required | Notes |
|---|---|---|
| `url` | yes | Absolute `https`. `http` only with `FELIX_ENVIRONMENT=development` and `FELIX_ALLOW_INSECURE=true`. No `user:pass@`. |
| `secret` | yes | Signs every delivery. A `whsec_…` base64 key (what Standard Webhooks libraries generate), any other string, or `secret:NAME` resolved through `FELIX_SECRETS_BACKEND`. Masked in audit, session and tool output in every process. |
| `tenants` | yes | Tenant ids that may name the endpoint, or `"*"` for all. There is no default: an endpoint open to every tenant lets any tenant's run arrive signed with its secret, so it has to be written out — and that receiver must check `tenant_id`. |
| `private` | no | `true` exempts this URL from the egress guard so it may resolve to a private address. Operator-only; redirects are still refused. |

A malformed registry fails the boot. A run naming an id that is unregistered or not allowed for its
tenant is refused at enqueue with the same `422 unknown webhook endpoint: <id>` either way, so the
answer does not reveal what other tenants have registered. Removing or narrowing an endpoint later
marks pending deliveries to it `dead` rather than sending them.

| Setting | Default | |
|---|---|---|
| `FELIX_WEBHOOK_ENDPOINTS` | empty | The registry above, as JSON. |
| `FELIX_WEBHOOK_MAX_ATTEMPTS` | `8` | Tries per endpoint before `dead`; backoff 1m doubling to 1h. |
| `FELIX_WEBHOOK_TIMEOUT_SECONDS` | `10` | Above 0, at most `60`; a larger value fails the boot. Whole-attempt bound, including a receiver that answers slowly. A sweep starts no delivery after the first 60 seconds of its 120-second claim, and the cap keeps one attempt inside that. |

Delivery runs in the Worker's `webhook_delivery` cron, so it needs `felix-scheduler` like every
other periodic task. Each attempt increments `felix_webhook_delivery{kind, endpoint, outcome}` with
`kind="run"` and `outcome` one of `delivered`, `retry`, `dead`. The payload and how to verify it:
[REST API → Completion webhooks](/guide/rest-api/#completion-webhooks).

The same registry carries imported skills' update events: `FELIX_SKILL_UPDATE_WEBHOOKS` binds a
tenant to endpoint ids here, and those deliveries count under `kind="skill_update"`. The `kind`
label is new with them; a query that ignores it now counts both, so filter `{kind="run"}` for runs
alone. A receiver shared by both dispatches on the body's `type`. See
[Skill import → Update notifications](/guide/skill-import/#update-notifications).

## Shared destinations

An agent with [`spec.destinations`](/guide/manifest-reference/running/#specdestinations) may publish to a
shared place — a team channel, a status feed — with its `post` tool, from a job's firing, a heartbeat
or a trigger's run. The manifest names ids only; the operator registers what each id is and which
tenants may name it. The registration is the advance approval, which is why a post needs no approval
by default.

```bash
FELIX_WEBHOOK_ENDPOINTS='{
  "ops": {"url": "https://hooks.example.com/felix", "secret": "secret:OPS_WEBHOOK", "tenants": ["acme"]}
}'
FELIX_DESTINATIONS='{
  "team-brief": {"kind": "webhook", "endpoint": "ops", "tenants": ["acme"], "link_hosts": ["status.acme.com"]}
}'
```

| Key | Required | Notes |
|---|---|---|
| id | — | Lowercase: `^[a-z0-9][a-z0-9_-]{0,63}$`. What `spec.destinations.ids` names. |
| `kind` | yes | The adapter that delivers a post. Core ships `webhook`; the `felix-channels` plugin adds `slack` (below); a plugin may [register more](/internals/plugins/#destination-kinds). |
| `tenants` | yes, unless `operator` | Tenant ids that may name the destination, or the string `"*"` for all, written out. A list holding `"*"` (`["*"]`) fails the boot, in this and every other operator registry: it named a tenant called `*`. |
| `operator` | no | `true` makes it the harness's own channel, for [job health alerts](/guide/deploy/scheduling/#job-health-watch): no manifest may name it and `tenants` is not read. Default `false`. |
| `links` | no | `strip` (default) removes every link from a post, as `notify` does; `keep` leaves them all. |
| `link_hosts` | no | With `links: strip` only: a non-empty list of hosts whose links are kept — a host, or `*.` and a host (`allow_hosts` patterns). With `keep` it fails the boot. |
| anything else | per kind | The kind's own fields. `webhook` takes `endpoint`; `slack` takes `channel` and `conversation`. A key spelled like one of the five above (`Links`, `link-hosts`) fails the boot rather than reaching the kind unread. |

**`kind: webhook`** sends a post as a signed `POST` to a
[`FELIX_WEBHOOK_ENDPOINTS`](#completion-webhooks) endpoint, which must be open to the tenant as well:
the destination says the tenant may post there, the endpoint that its secret may sign for it. The
endpoint's `url`, `secret` and `private` flag apply as for a completion webhook, egress guard and
refused redirects included.

**`kind: slack`**, with the [`felix-channels`](/guide/deploy/integrations/#slack) plugin installed in the API and the Worker,
posts into a Slack conversation through a `FELIX_CHANNELS` app, with that app's bot token:

```bash
FELIX_DESTINATIONS='{
  "team-brief": {"kind": "slack", "channel": "acme-slack", "conversation": "C0123ABCD", "tenants": ["acme"]}
}'
```

`channel` is a [`FELIX_CHANNELS`](/guide/deploy/integrations/#slack) id; `conversation` is the Slack id of where the post
goes — a channel `C…`, a private channel `G…` or a DM `D…`. The destination holds no secret of its
own: the token is the channel's, resolved and registered for masking before the post's text is
cleaned, so a model that writes the token into a post has it redacted even in a Worker that ran no
plugin startup hook. A Slack app belongs to one tenant, so the destination posts through it only
for that tenant; any other tenant's compile is refused with the words an unregistered channel gets.
The app needs `chat:write` and must be a member of a channel or private channel it posts to.

What reaches Slack is the post as the harness cleaned it, escaped (`&`, `<`, `>`) and sent with
`parse: none`, `link_names: false` and unfurling off: `<!channel>`, `<!here>`, `<@U…>` and `@here`
arrive as text and ping nobody, and Slack fetches no link the registration keeps. A `title` leads
the message, in bold. Slack's `ok: true` is `posted`, with `ref` `<conversation>:<ts>`. An
`ok: false` whose code is a definite refusal — `channel_not_found`, `not_in_channel`,
`is_archived`, a revoked or wrong token, a missing scope or permission, `msg_too_long`,
`ratelimited` and the rest of `DEFINITE_REFUSALS` — is `not_posted`, with a fixed detail for each
family and never Slack's own text (the code is logged as `slack_post_refused`); any other `ok: false`
is `unknown`, recorded `maybe_posted`, as is an answer that is not JSON. A status other than `200`
and a send error follow the shared rules a `webhook` does: a `4xx` other than `408` and `409`, a
connect error or a connect timeout is `not_posted`; a `5xx`, or a timeout once the request went, is
`unknown`.

The boot checks the registry's shape — ids, `kind`, `tenants`, the link policy — and a malformed one
fails it (`FELIX_DESTINATIONS: …`). The kind and its own fields are checked when a manifest naming
the id compiles, since a plugin's kind may register after the settings are read: an unregistered id,
one not open to the tenant, an uninstalled kind or fields the kind refuses (a `webhook` with no
`endpoint`, or one not open to the tenant; a `slack` with no `channel`, a `conversation` that is
not a `C…`, `G…` or `D…` id, or a channel not registered for the tenant) all fail the compile, `422`
on `/chat`, with the same `unknown destination: <id>` for an unregistered id, another tenant's and
an operator destination.

| Setting | Default | |
|---|---|---|
| `FELIX_DESTINATIONS` | empty | The registry above, as JSON. Set it on the API and the Worker alike: a job's firing compiles and posts in the Worker. |

<Aside type="caution">
  **Choose `links: keep` knowingly.** A chat service that unfurls links fetches each one
  server-side the moment it is posted. A link a model wrote — under a prompt injection, with data
  in its path or query — then carries that data to any host, even if no person ever clicks it.
  `link_hosts` bounds that to hosts you trust; `strip` closes it.
</Aside>

### What a webhook receiver gets

A `webhook` destination's post is sent by the `post` call itself, once, bounded by
`FELIX_WEBHOOK_TIMEOUT_SECONDS` — not queued to the Worker's `webhook_delivery` cron, and never
retried:

```http
POST /felix HTTP/1.1
content-type: application/json
user-agent: Felix-Webhooks/1
webhook-id: post_3f0c…
webhook-timestamp: 1790000000
webhook-signature: v1,…

{"destination":"team-brief","edition":"brief:2026-10-29","manifest_id":"briefer","tenant_id":"acme",
"text":"…","title":"Morning brief","type":"post.created","unattended":true}
```

The signature is Standard Webhooks, verified exactly as a
[completion webhook](/guide/rest-api/#completion-webhooks) is. The body is compact, key-sorted JSON:
`type` is `post.created`; `text` and `title` are the post as it left (secrets redacted, links as
the registration says, screened); `unattended` says whether anyone was watching the run that posted
— never who.

- **Dedupe on `webhook-id`.** It is `post_` and 40 hex characters of a hash of the tenant,
  destination, manifest and edition, so it is the same on every attempt at one edition: after a
  `not_posted`, or after an operator clears a stuck edition. `webhook-timestamp` and the signature
  change per attempt.
- **Answer 2xx for an id you already took**, too. Any 2xx records the edition `posted`, with the
  `webhook-id` as its `ref`. A `409` or a `408`, like a `5xx`, a `3xx` or no answer in time, is
  recorded `maybe_posted`, and the edition is not posted again until an operator clears it.
- **Any other `4xx`** says the post did not land: the edition is released, and the agent may try it
  again.
- **Check `tenant_id`** on an endpoint registered for `"*"`, and **dispatch on `type`** on an
  endpoint that also receives run or skill-update events.

### A stuck edition

Felix posts each manifest's edition to a destination at most once, and a delivery whose outcome it
does not know is recorded `maybe_posted` and never retried — see
[`destination_posts`](/internals/persistence/#relational-highlights). A `posting` row older than two
minutes, left by a process that stopped mid-delivery, reads the same way. Until a route for it
lands, an operator who has checked the destination clears the row by hand, as the table's owner and
through the RLS bypass the policy honours; the next call naming the edition then posts it:

```sql
BEGIN;
SET LOCAL app.rls_bypass = 'on';
DELETE FROM destination_posts
 WHERE tenant_id = 'acme' AND destination = 'team-brief'
   AND manifest_id = 'briefer' AND edition = 'brief:2026-10-29'
   AND status IN ('posting', 'maybe_posted');
COMMIT;
```

If the post did land, leave the row — or set `status = 'posted'` — so it is not posted twice.
