Felix runs as containers you operate — CPython behind your own ingress, with no serverless or edge
runtime anywhere in the harness. A CDN may sit in front for DNS, TLS and WAF only.

| Piece | Local | Production |
|-------|-------|------------|
| API | `felix-api` on `:8080` | Same image behind your ingress |
| Worker | Taskiq consumer | Same image, `felix-worker` |
| Scheduler | Taskiq scheduler | Same image, `felix-scheduler` |
| Postgres + pgvector | Compose service | Managed Postgres (Neon, RDS, Cloud SQL, …) |
| Valkey / Redis | Compose | Memorystore / ElastiCache / self-hosted |
| Object store | `fs` (default) | `s3` / `gcs` (+ image extras) |

## Compose

```bash
cp .env.example .env   # set POSTGRES_PASSWORD
make up
make migrate
```

Lean hosts: `make up-lite`. MinIO profile: `make up-full` with `FELIX_DOCKER_EXTRAS=aws`.

### Overlays

Each is a Compose overlay on the base stack, composable with the others. Run from the repo root —
the Makefile passes `--project-directory .`.

| Target | Adds |
|---|---|
| `make up-lite` | Tighter `mem_limit`; no host ports for DB/cache |
| `make up-pooled` | PgBouncer in transaction mode |
| `make up-replicas` | Two API replicas behind one nginx origin |
| `make up-observability` | OTel Collector, Prometheus, Grafana, Jaeger, Loki, Postgres/Valkey exporters |
| `make up-self` | The self-build stack: a `shell` runner container that holds no secrets and runs every shell tool, and no host ports for DB, cache or object store. Writes `FELIX_SHELL_RUNNER_TOKEN` into `.env` first |

### Observability stack

```bash
make up-observability   # Grafana :3000 · Prometheus :9090 · Jaeger :16686
```

Budget roughly 1.7 GiB of additional `mem_limit`, so this does not belong on the same host as
`make up-lite`. It also rebuilds the image with the `otel` extra — the lean default omits it, and
without it OTLP export logs one warning at startup and ships nothing while every other signal keeps
working.

`/metrics` is authenticated (its labels carry tenant-supplied manifest ids and remote MCP tool
names), and Prometheus has no env expansion in scrape configs — so `scripts/metrics-token.sh`, which
`make up-observability` runs for you, mints a **second** API key with an empty `scopes` array beside
your operator key and writes the bare token to a gitignored file. `/metrics` has no scope gate, so
that key reads metrics and is refused everywhere else.

See [observability](/internals/observability/) for the metric catalog and span schema.

### Sending traces to a backend you already run

Felix exports OTLP, so any backend that reads it works — a collector, a hosted vendor, an
LLM-observability console you self-host elsewhere. None of that runs inside the Felix compose
project: every `FELIX_OTEL_*` setting is passed through `compose.yml`, so `make up` exports with no
overlay at all.

```bash
FELIX_DOCKER_EXTRAS=otel            # the exporter lives behind an extra
FELIX_OTEL_ENABLED=true
FELIX_OTEL_PROTOCOL=http            # grpc for a collector on 4317; http for a hosted ingest
FELIX_OTEL_ENDPOINT=https://ingest.example.com/v1/otel
FELIX_OTEL_INSECURE=false
FELIX_OTEL_HEADERS=authorization=Basic <credential>
FELIX_OTEL_SERVICE_NAME=felix-prod  # when several deployments share one backend
```

Felix needs **no vendor SDK and no extra dependency**. Spans carry the `gen_ai.*`
semantic-convention attributes, so a backend that understands them renders a chat as a generation
with model, token usage and cost rather than as a bare span — the integration is an endpoint and a
header, and nothing in the harness knows which product is on the other end.

Run `uv run felix doctor` after: it reports whether the exporter is actually installed, in every
environment. Enabling export on a lean image logs one warning and sends nothing, and an empty
dashboard is otherwise the only sign.

<Aside type="note" title="Identity reaches the backend by default">
`user.id` and the tenant id are on spans unless you set `FELIX_OTEL_CAPTURE_IDENTITY=false`. Prompts
and completions are **not** — they sit outside governance content screening, so
`FELIX_OTEL_CAPTURE_CONTENT=true` is an explicit opt-in.
</Aside>

A process has one OTLP destination. To send to Jaeger **and** a second backend, run the
observability overlay too, leave `FELIX_OTEL_ENDPOINT` pointing at the collector, and add an
`otlphttp` exporter there — fanning out is the collector's job. The second backend's credential goes
in the collector's config, not in `.env`: the overlay blanks `FELIX_OTEL_HEADERS` so a header meant
for a hosted ingest is not sent to a local collector that never asked for one.

## Sizing

Each worker process carries **its own** connection pool, so raise the two together or the second
one becomes the ceiling.

| Setting | Default | Notes |
|---|---|---|
| `FELIX_WORKERS` | `1` | Granian/uvicorn worker processes |
| `FELIX_DB_POOL_SIZE` | `10` | Per worker |
| `FELIX_DB_MAX_OVERFLOW` | `20` | Per worker, on top of the pool |
| `FELIX_DB_POOL_TIMEOUT_SECONDS` | `30` | How long a request queues before failing |
| `FELIX_DB_POOL_PRE_PING` | `true` | Set `false` against a direct Postgres |
| `FELIX_DB_PREPARED_STATEMENTS` | `true` | Set `false` behind a pooler that does not track them — see below |

The effective ceiling is `WORKERS × (POOL_SIZE + MAX_OVERFLOW)` connections. Past it, requests
queue for `FELIX_DB_POOL_TIMEOUT_SECONDS` and then fail — so check the ceiling against your
database's own `max_connections` before raising either number.

`FELIX_DB_POOL_PRE_PING` costs a round trip on every checkout to discover a connection a pooler
closed server-side. That earns its cost behind PgBouncer, RDS Proxy, or Cloud SQL and wastes it
against a Postgres you connect to directly.

## Behind a connection pooler

Four workers on the defaults is 120 connections against a stock Postgres `max_connections` of
100 — and raising `max_connections` trades one wall for another, since every backend costs
memory. A transaction-mode pooler multiplexes many cheap client connections onto few server ones
instead.

```bash
make up-pooled   # adds PgBouncer in transaction mode in front of Postgres
```

Felix's own pool then becomes a pool of *client* connections to PgBouncer, which are cheap.
`PGBOUNCER_POOL_SIZE` is the real server-side limit — raise the former freely, size the latter
against your database.

Run migrations against Postgres directly rather than through the pooler. Nothing breaks under
transaction pooling; a migration is a one-off admin action with no reason to go through a
multiplexer sized for request traffic.

### Prepared statements

<Aside type="caution" title="This one fails on the sixth query, not the first">
psycopg3 automatically prepares a statement after its **fifth** execution. Under transaction
pooling the sixth lands on a different server connection, where that statement was never
created, and the query fails. Five identical queries succeed first, so the symptom looks
unrelated to the change that caused it.
</Aside>

Either the pooler tracks prepared statements or Felix stops making them — never neither:

| Pooler | Setting |
|---|---|
| PgBouncer ≥ 1.21 with `max_prepared_statements > 0` | leave `FELIX_DB_PREPARED_STATEMENTS=true` |
| PgBouncer with `max_prepared_statements = 0` | set `FELIX_DB_PREPARED_STATEMENTS=false` |
| **RDS Proxy** | set `FELIX_DB_PREPARED_STATEMENTS=false` |
| Direct Postgres, or session-mode pooling | leave it `true` |

`make up-pooled` sets `max_prepared_statements` non-zero, so the default is correct there.

RDS Proxy is the case that forces the decision rather than merely allowing it: it *pins* the
session when it sees a prepared statement, holding a server connection for the life of the
client one — which defeats the multiplexing you deployed it for. There the setting costs you
nothing and buys back the pooling.

## Helm

Chart: `deploy/helm/felix` in [felix-run/felix](https://github.com/felix-run/felix).

```bash
helm upgrade --install felix ./deploy/helm/felix \
  --set secrets.databaseUrl="$FELIX_DATABASE_URL" \
  --set secrets.redisUrl="$FELIX_REDIS_URL" \
  --set secrets.consumerSharedSecret="$FELIX_CONSUMER_SHARED_SECRET" \
  --set secrets.jwksPublic="$FELIX_JWKS_PUBLIC" \
  --set secrets.jwksPrivate="$FELIX_JWKS_PRIVATE"
```

A **pre-install/pre-upgrade Job** runs `felix migrate head` (`migrate.enabled=true`).
The chart runs **api**, **worker**, and **scheduler**. For `FELIX_OBJECT_STORE=fs`,
enable `persistence.enabled=true`.

Set `serviceMonitor.enabled=true` for a Prometheus Operator scrape of `/metrics`. It reads a bearer
token from a Secret you create — use a Felix API key with an empty `scopes` array, the same
least-privilege shape `scripts/metrics-token.sh` mints for Compose:

```bash
kubectl create secret generic felix-metrics-scrape --from-literal=token="$UNSCOPED_API_KEY"
helm upgrade --install felix ./deploy/helm/felix \
  --set serviceMonitor.enabled=true \
  --set serviceMonitor.bearerTokenSecret.name=felix-metrics-scrape
```

Cloud notes: `deploy/aws/README.md`, `deploy/gcp/README.md`.

## Auth (production)

| Mode | Notes |
|------|-------|
| `jwt` | Preferred — set `FELIX_JWKS_PUBLIC` / verifiers. Add [GitHub login](/internals/auth/#github-login) to let people mint their own tokens from org membership |
| `api_key` | `FELIX_AUTH_API_KEYS` map. Tenants are the orgs sharing an install, and keys and tenants are the install operator's configuration, with no key table or key API: adding an org or a key is an edit and a restart. An org's members log in through [GitHub login](/internals/auth/#github-login) or your IdP instead |
| `none` | **Loopback only** — see below |

:::caution[`none` cannot be exposed]
`FELIX_AUTH_MODE=none` is refused whenever `FELIX_HOST` is reachable off-host — in *every*
environment. `FELIX_ALLOW_INSECURE` only relaxes the non-development environment check; it does
**not** permit a public unauthenticated bind. `FELIX_HOST` defaults to `127.0.0.1`, containers set
`0.0.0.0` explicitly and pair it with a real auth mode, and Compose defaults to `api_key` with a key
generated by `make up`.
:::

`/internal/*` needs `FELIX_CONSUMER_SHARED_SECRET` when auth is not open.

## Cron schedules

Scheduled jobs (`PUT /jobs/{name}`) use standard **five-field** cron, evaluated in UTC:

```
┌─ minute (0-59)
│ ┌─ hour (0-23)
│ │ ┌─ day of month (1-31)
│ │ │ ┌─ month (1-12)
│ │ │ │ ┌─ day of week (0-6, Sunday = 0)
│ │ │ │ │
* * * * *
```

| Expression | Meaning |
|---|---|
| `*/10 * * * *` | Every ten minutes |
| `0 3 * * *` | Daily at 03:00 |
| `0 9 * * 1` | Mondays at 09:00 |

:::note
The worker's `run_scheduled_jobs` cron sweeps due rows every minute, but the sweep is *enqueued* by
`felix-scheduler`. Run all three containers — API, worker **and** scheduler — or no job, retention
sweep or memory consolidation ever fires. Durable runs are the exception: each worker polls for them
itself (below), and the scheduler's once-a-minute `fiber_scheduler` sweep is only the backstop.
:::

## Durable runs

A durable run is a `pending` fiber until a worker claims it, and nothing tells the worker when one
is submitted — so each worker polls. The claim is the same lease plus `FOR UPDATE SKIP LOCKED` the
cron sweep takes, so any number of workers, polling or sweeping, never run one fiber twice.

| Setting | Default | |
|---|---|---|
| `FELIX_FIBER_POLL_SECONDS` | `1.0` | How often each worker checks for due fibers. `0` turns the poll off and leaves only the once-a-minute sweep, which is how durable runs were started before 0.5.0 — each waited up to a minute before its first model call. |
| `FELIX_FIBER_CONCURRENCY` | `8` | Fibers one worker advances at once. A run parked on an approval holds its slot until someone answers, so this bounds how many such waits can pile up before a new run waits for a slot. A full worker leaves further runs unclaimed for another worker. |
| `FELIX_FIBER_MAX_ATTEMPTS` | `5` | Consecutive failed steps before a fiber is `dead`; retries back off 1m doubling to 1h. |

## Completion webhooks

A durable run can announce its end to endpoints its manifest names in `spec.execution.webhooks`.
The manifest carries only ids; the operator registers what each id means:

```bash
FELIX_WEBHOOK_ENDPOINTS='{
  "ops":   {"url": "https://hooks.example.com/felix", "secret": "secret:OPS_WEBHOOK", "tenants": ["acme"]},
  "audit": {"url": "http://audit.internal:8080/runs", "secret": "whsec_...", "tenants": "*", "private": true}
}'
```

| Key | Required | Notes |
|---|---|---|
| `url` | yes | Absolute `https`. `http` only with `FELIX_ENVIRONMENT=development` and `FELIX_ALLOW_INSECURE=true`. No `user:pass@`. |
| `secret` | yes | Signs every delivery. A `whsec_…` base64 key (what Standard Webhooks libraries generate), any other string, or `secret:NAME` resolved through `FELIX_SECRETS_BACKEND`. Masked in audit, session and tool output in every process. |
| `tenants` | yes | Tenant ids that may name the endpoint, or `"*"` for all. There is no default: an endpoint open to every tenant lets any tenant's run arrive signed with its secret, so it has to be written out — and that receiver must check `tenant_id`. |
| `private` | no | `true` exempts this URL from the egress guard so it may resolve to a private address. Operator-only; redirects are still refused. |

A malformed registry fails the boot. A run naming an id that is unregistered or not allowed for its
tenant is refused at enqueue with the same `422 unknown webhook endpoint: <id>` either way, so the
answer does not reveal what other tenants have registered. Removing or narrowing an endpoint later
marks pending deliveries to it `dead` rather than sending them.

| Setting | Default | |
|---|---|---|
| `FELIX_WEBHOOK_ENDPOINTS` | empty | The registry above, as JSON. |
| `FELIX_WEBHOOK_MAX_ATTEMPTS` | `8` | Tries per endpoint before `dead`; backoff 1m doubling to 1h. |
| `FELIX_WEBHOOK_TIMEOUT_SECONDS` | `10` | Whole-attempt bound, including a receiver that answers slowly. |

Delivery runs in the worker's `webhook_delivery` cron, so it needs `felix-scheduler` like every
other periodic task. Each attempt increments `felix_webhook_delivery{endpoint, outcome}` with
`outcome` one of `delivered`, `retry`, `dead`. The payload and how to verify it:
[REST API → Completion webhooks](/guide/rest-api/#completion-webhooks).

## Model routes

`FELIX_DEFAULT_MODEL_ID` (default `claude-sonnet`) picks the model a manifest gets when it does not
name one. `FELIX_MODEL_ROUTES` is a JSON object that overrides or extends the logical-id table, so
manifests stay portable across deployments:

```bash
FELIX_DEFAULT_MODEL_ID=claude-sonnet
FELIX_MODEL_ROUTES='{
  "claude-sonnet": {"provider": "anthropic", "model": "claude-sonnet-5"},
  "house-fast":    {"provider": "ollama",    "model": "llama3.2"}
}'
```

Providers are `anthropic`, `openai`, `ollama`, `workers_ai` (Cloudflare Workers AI), `groq`,
`together`, `deepseek`, `cerebras`, `fireworks`, `openrouter`, `xai`, `mistral` and `google`, plus any
registered by a plugin. Point `FELIX_OLLAMA_BASE_URL` or `FELIX_LITELLM_BASE_URL` at a local gateway to
keep traffic in your own network. Everything past the first three is configured through
`FELIX_MODEL_PROVIDER_OPTIONS`:

```bash
FELIX_MODEL_PROVIDER_OPTIONS='{"workers_ai":{"api_key":"...","account_id":"...","gateway_id":"default"}}'
```

That one entry is all the built-in Workers AI routes need: `kimi-k2-cf` (Kimi K2.6, 262K window),
`gpt-oss-120b-cf`, `gpt-oss-20b-cf` and `glm-flash-cf`. All four call tools and are priced, so
`limits.max_cost_usd` is enforced on them. To run on Workers AI wherever a manifest names no model,
and move the Ollama ids and the memory embedder there as well:

```bash
FELIX_DEFAULT_MODEL_ID=kimi-k2-cf
FELIX_MODEL_ROUTES='{"llama-3-pro":{"provider":"workers_ai","model":"@cf/openai/gpt-oss-120b"},"llama-3-fast":{"provider":"workers_ai","model":"@cf/zai-org/glm-4.7-flash"}}'
FELIX_MEMORY_EMBEDDER=workers_ai
```

Provider names in `FELIX_MODEL_ROUTES` are resolved against the registry at startup, so a typo fails
immediately rather than on the first request that happens to take that route. A manifest referring to
`house-fast` works everywhere the route is defined. See [Model client](/internals/model-client/).

## Embeddings

One embedder per deployment serves the vector channel of memory recall and of the
[documents corpus](/guide/management-api/#documents). Without one, both still retrieve by full text
(and memory by topic key); hits report `lexical` only.

| Setting | Default | Notes |
|---|---|---|
| `FELIX_MEMORY_EMBEDDER` | `auto` | `auto` embeds locally with `sentence_transformers` when `felix-harness[embeddings]` is installed, and otherwise runs no vector channel. `none` turns it off. `sentence_transformers` requires the extra. Any registered provider that serves `/embeddings` (`openai`, `ollama`, …) is also accepted, resolved through the same descriptor as its model client. An unregistered name fails startup validation. |
| `FELIX_MEMORY_EMBEDDING_MODEL` | `bge-base-en-v1.5` | The local model. For a provider embedder, only an explicitly set value is sent; unset, the provider's own default embedding model is used. |
| `FELIX_MEMORY_EMBEDDING_DIM` | `768` | Declares the width of the `memory_vectors.embedding` column, which is `vector(768)` from the baseline migration. Changing it means re-embedding every row, not flipping a setting. |

`auto` is local only. It never picks a hosted embedder: that would send every stored memory to
whichever provider has a key configured, and the column is sized for the local model. Choosing a
provider is always an explicit setting. The local weights are fetched on first use, so the first
embed after a start is slow and needs outbound access to the model hub.

The default image is built lean, without the `embeddings` extra, so `auto` there means no vector
channel. Build with `--build-arg FELIX_EXTRAS=embeddings` to turn it on. On an image that has the
extra, set `FELIX_MEMORY_EMBEDDER=none` to keep full-text-only recall.

## Chat UI / docs Workers

Frontends live in [felix-run/web](https://github.com/felix-run/web). Deploy chat-ui with
`vars.FELIX_ORIGIN` pointing at your public Felix API; docs is a static Workers site.

### Browsers need a same-origin proxy

Felix has no CORS layer, on purpose, so a page on another origin cannot call it directly. A
preflight `OPTIONS` gets a 401 (or a 405 under `FELIX_AUTH_MODE=none`) with no
`Access-Control-Allow-*` headers, and the browser stops there. A plain `GET` still reaches Felix,
but the page cannot read the response. There is no browser login (no cookies), so a page calling
Felix directly would have to hold a bearer token or API key, where any script on the page can read
it.

Put a server-side proxy on the page's own origin instead. It holds the credential, adds
`Authorization`, and forwards to Felix. The chat-ui Worker does exactly this: it forwards `/api/*`
to `FELIX_ORIGIN`, and when `CHAT_UI_KEY` is set it first checks the browser's `x-chat-key`. An
nginx or Caddy `location /api/` block that sets the header works the same way. The CLI,
`felix-client`, curl and other services are not browsers, so none of this applies to them.
